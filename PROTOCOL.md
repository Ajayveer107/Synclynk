# SyncLynk Wire Protocol

One WebSocket connection, PC as server, phone as client. Every message
is a single JSON object with a `type` field. No accounts, no database —
the only "auth" is the one-time token from the QR code, checked once at
connect time.

## 1. Pairing (required first message)

Phone → PC, immediately after the socket opens:
```json
{"type": "pair", "token": "a1b2c3d4"}
```

PC → Phone:
```json
{"type": "pair_result", "ok": true}
```
If `ok` is `false`, the PC closes the socket. The phone should prompt
the user to rescan the QR code.

## 2. Clipboard sync (bidirectional)

Either side, whenever its clipboard changes:
```json
{"type": "clipboard", "data": "text that was copied"}
```
The receiver applies it to its own clipboard and remembers the value so
it doesn't immediately echo it back (avoids infinite ping-pong).

## 3. Notification mirroring (phone → PC only)

```json
{"type": "notification", "app": "WhatsApp", "title": "Sam", "text": "On my way!"}
```

## 4. Camera mirroring (phone → PC)

```json
{"type": "camera_start"}
{"type": "camera_frame", "data": "<base64 JPEG bytes>"}
...
{"type": "camera_stop"}
```
Frames are sent at a throttled rate (~12 fps) to keep plain Wi-Fi
comfortable without needing WebRTC/codecs.

## 5. File transfer (bidirectional)

Files are sent in base64-encoded chunks so large files don't need to
sit fully in memory on either side.

```json
{"type": "file_start", "id": "f-93a1", "name": "photo.jpg", "size": 482913}
{"type": "file_chunk", "id": "f-93a1", "seq": 0, "data": "<base64 chunk>"}
{"type": "file_chunk", "id": "f-93a1", "seq": 1, "data": "<base64 chunk>"}
...
{"type": "file_end", "id": "f-93a1"}
```
- `id` is a short random string generated by the sender, used to
  associate chunks with the right file if multiple transfers overlap.
- Chunks are ~48KB of raw file data each (before base64 inflates it),
  sent in order over the single WebSocket connection, which preserves
  ordering, so the receiver just appends as chunks arrive.
- The receiver writes to a temp file named after `id` and renames it to
  `name` once `file_end` arrives, so a half-finished transfer never
  shows up as a "complete" file.
- Windows saves incoming files to `~/SyncLynk Received/`.
  Android saves incoming files to the public **Downloads** folder,
  under a `SyncLynk` subfolder, via MediaStore.

## Extending it

Adding a new feature (file transfer, media/volume control, remote
input, etc.) just means picking a new `type` value and adding a
handler on each side — `server.on_message(...)` on Windows,
a `when (type)` branch on Android. No schema migrations, no backend
changes, because nothing is persisted.
